---

## 1. 课程定位

初级课已经讲完知识点：HTML/CSS/JS、Three.js、Flask、JSON 数据库、WebSocket、LLM API / Agent。

高级课**不再讲知识点**，而是把主线放在**软件工程的全流程**上：一个产品从「想清楚要做什么」到「上线被别人使用」的完整过程。

核心方法：**同一套工程流程，用三个不同方向的项目反复练手**，让学生真正内化流程，而不是记住某个 API。

一句话主线：**规则文档 → 需求文档 → 技术设计 → 任务拆解 → UI 风格确认 → 分阶段实现 → 自动化测试 → 部署上线 → Git 版本管理（贯穿）**。

---

## 2. 课程目标（学完之后学生能独立做到）

- 会写并维护「规则文档（rules.md）」，用它约束 AI 的行为（每次与 AI 协作都带上）
- 和 AI 协作打磨出一份完整、可执行的需求文档（PRD）
- 根据需求产出技术设计文档（架构、选型、数据库设计、API 设计）
- 让 AI 把项目拆成可交付的阶段/任务，并逐步实现（不允许一次性生成全部）
- 确定统一的 UI 风格规范，用全局 CSS 保持整体视觉一致（避免每个页面各写一套）
- 理解「验收标准」：项目要有验收文档，全部测试通过才算验收通过（类比装修的验收，每个学生都该懂）
- 理解「软件工程必须有测试环节」——以前人工测、现在约 90% 由 AI 自动化测；能读懂测试报告并做决策
- 用 Git 做个人版本管理：阶段性保存代码、随时回滚（学生暂不组队，协作功能后置）
- 把项目部署上线，能被别人访问

## 4. 统一软件工程流程（每个项目都走一遍）

### M1 · 规则文档（rules.md）——贯穿全程的核心
- 本质：给 AI 的「人设 / 工作守则」，相当于每次与 AI 协作都要带的规则（system prompt）
- 内容：技术栈与代码规范、文件结构约定、交付方式（如"分阶段实现，禁止一次性生成全部"）、测试要求、UI 风格约束、**安全约束**、**环境与依赖管理**、需要学生确认的节点等
- 必含的安全约束（学生了解即可，落实由 AI 负责）：密码必须哈希存储、API Key / 数据库密码走 .env 不进代码库、SQL 用参数化查询防注入、登录接口做基本校验
- 必含的环境约束：使用虚拟环境（venv）+ `requirements.txt` 锁定依赖，保证换机器/换环境也能跑（向学生解释"为什么需要"）
- **第 1 课建立初版**，与需求文档同步打磨；之后**随项目不断修改和完善**——每遇到一个"AI 又犯的错"就加一条规则
- 例：每完成一个功能 → 自动生成测试 → 自动执行 → 出测试报告 → 经学生确认后才继续
- 讲课示例：先立规矩——"**没有我明确许可，不要写代码**"。很多时候跟 AI 聊天是在协商方案，不是让它立刻动手；这条写进规则，避免每说一句 AI 就去改代码

### M2 · 需求文档（PRD）+ 验收文档
- 与 AI 来回打磨：用户角色、功能清单、优先级（Must/Should/Could）、用户故事、验收标准
- 产出：**需求文档**（后续所有工作的唯一依据）+ **验收文档**（基于 PRD，列出每项功能"怎样算通过"）
- 用「装修」类比讲验收概念：装修有验收标准（墙平、不漏水），项目也是自己定义出来的，更要有验收标准
- 验收通过的定义：**所有 test case 全部跑过**才算通过；性能等暂时提一下但不做要求；验收标准要**可测量**（如"注册后能登录""错题本能记录 100 题"），不能写"体验好"这类模糊词
- 教学要点：学生没做过项目、没有工程化概念，"验收标准"是他们最容易缺、也最重要的一课
- 讲课示例：甲方乙方的故事——"你做个东西吧"→ 做完对方不认账，因为没有明确的需求，双方都不知道该做什么；需求文档就是"做什么"的共同约定
- MVP 意识：8 小时只保证 MVP（Must 项全部完成），Should/Could 按剩余时间取舍，学会"砍需求"也是核心能力

### M3 · 技术设计文档
- 架构（前端 / 后端 / 数据库）
- 技术选型（让 AI 给建议 + 权衡）
- 数据库设计（表结构 / 关系）
- API 接口设计（路由、请求 / 响应格式）
- 讲课示例：数据库有好几种（JSON / SQLite / MySQL），后端也有多种实现方式，**不同场景选型不同**——项目开始前先定好技术栈，后面才不返工

### M4 · 任务拆解
让 AI 把需求拆成 phase / task，**不允许一次性生成全部**，按阶段交付、每阶段可运行。
- 讲课示例：像规划一个工程一样统筹安排——任务不一定是串行的，可以让 AI 并行推进；涉及"团队合作"时，要提前定好各模块之间的**接口**和**对接进度**

### M5 · UI 风格确认（实现前先定视觉规范）
- 确定整体视觉风格：配色、字体、间距、组件样式（按钮/卡片/表单/导航等）
- 产出统一的全局 CSS（CSS 变量 + 通用样式），所有页面共用同一套，**禁止每个页面各写一套**
- 关键：AI 逐页生成代码时容易风格漂移，必须先有「UI 风格规范」+ 全局样式文件来约束它
- 讲课示例：用户看不懂背后的需求和技术细节，但**他在意界面**——界面有两层：好不好看（按钮多大、配色如何）+ **页面之间的跳转逻辑**；动手前先确认这两层

### M6 · 分阶段实现
按拆解好的任务逐步实现，每个阶段可运行、可验收。
- 讲课示例：不是一股脑把整个项目做完——中途出错了都不知道，到后面改会产生大量无用功；所以要分阶段，每阶段做一次**对齐 / 验收**，把控项目节奏（像工程排期一样，小项目几天、大项目两周，阶段对齐一次）

### M7 · 测试（含 seed data）
- 由 **M1 规则文档**驱动：每完成一个功能 → AI 自动生成测试 → 自动执行 → 产出测试报告
- 与 **M2 验收文档**对应：**全部 test case 跑过 = 该功能验收通过**（这就是"完成"的标准）
- 测试不是 100% 自动化：约 **90% 由 AI 自动化完成**，还有约 **10% 需要人手工验证**（AI 测不了的主观体验、真实操作流程）
- **seed data（预置数据）也是测试的一部分**，分两批：
  - **基础数据**（第 1 课建表后立即灌入：单词、题目、初始用户等）：让功能可测、界面有内容
  - **演示数据**（第 3 课补充，让演示界面更丰富、不空板）
  - 可能还包括图片 / 文件等静态资源
  - 作用：让界面有内容可看（演示不空板）+ 让自动化测试有数据可测
- 经学生确认后，AI 全自动 / 半自动修复 bug
- 学生层面：只需理解「测试的意义」+ 会读报告，不深入框架细节
- 讲课示例：传统软件工程里测试分三层——**单元测试**（工程师做完小功能自己测）、**集成测试**（模块之间对接）、**系统测试**（全部功能一起跑）；测试不能留到最后才做，且真实工程中**测试耗时极多**。现在有 AI，约 90% 的测试可以自动化，剩下约 10%（主观体验、真实操作流程）仍需人工验证，所以项目一开始就要规划"写代码 + 测试"同步推进

### M8 · 部署上线
- 讲简单的部署概念（点到为止，不深入）
- 项目放 GitHub，通过一个「发布/部署平台」上线（Python 无编译，链路简单）
- 产出 README：写清项目是什么、怎么跑、怎么部署，也是专业工程的标配
- 讲课示例：产品跑在自己的电脑上，别人是看不到的；**部署**才能让别人访问。真实部署是系统化工程，但对课程来说知道有这一步、走通流程即可

### M9 · Git 版本管理（贯穿全程，个人使用）
- 学生目前**不组队**，Git 现阶段主要是**个人用途**：阶段性保存代码 + 出问题时回滚
- 第 1 课初始化仓库、学 commit / 查看历史 / 回滚；之后每个阶段提交一次，形成可回退的节点
- 团队协作（分支 / PR / code review / GitHub 远程同步）等后续有组队需求时再引入
- 讲课示例：课上各管各的版本；但工作中多人协作，**你改一处可能影响别人的代码**，所以版本管理、回滚、分支都非常重要

## 5. 每部分的 4 次课节奏（8 小时）

| 课次 | 主题 | 对应模块 |
|---|---|---|
| 第 1 课 | 前期准备：规则文档（rules.md）+ 需求文档 + UI 风格确认 + 关键点 demo 预研 + 技术设计/数据库/接口 + 任务拆解；**收尾：Git 初始化 + venv/requirements + 建库建表 + 灌第一批 seed data** | M1 + M2 + M3 + M4 + M5（+ M9 / M7 起步） |
| 第 2 课 | 分阶段实现 + 测试（每阶段循环：AI 实现 → 自动测试 → 测试报告 → 学生确认 → Git 提交） | M6 + M7 |
| 第 3 课 | 分阶段实现 + 测试（继续迭代）+ **补充演示用 seed data** | M6 + M7 |
| 第 4 课 | **人工验收（10%）+ 集成测试** + 修改迭代 + 演示预演 + 部署 + README + 复盘 | M7 + M8 |

> 规则文档（rules.md）是贯穿全程的：第 1 课建初版，每遇一个"AI 犯的错"就补一条，持续完善。
> 每部分结束时做 10 分钟**复盘**：哪个环节最卡？规则文档更新了哪几条？下次怎么改进？（形成"复盘 → 完善规则"的闭环）
> 关键点 demo 预研：对不确定的技术点，先做小 demo 验证可行性，再进入正式实现。
> Git 贯穿全程：第 1 课初始化仓库 + 学 commit / 回滚，之后每个阶段提交（个人使用，暂不涉及协作）；第 4 课可顺带讲 GitHub 远程备份。
> Part 1 第一次走流程会慢；到 Part 2 / Part 3 流程熟悉后，把更多时间留给实现和测试。

## 6. 技术基线

| 维度 | 结论 |
|---|---|
| 前端 | 不设强制栈，默认原生 HTML/CSS/JS，复杂交互时由 AI 引入 Vue/React；学生不学框架 |
| 后端 | Flask（Python） |
| 数据库 | 统一 MySQL；进项目前先做一个小案例热身（建库建表 + 增删改查 + Flask 连接） |
| 环境与依赖 | venv + `requirements.txt` 锁定依赖（第 1 课建立，向学生解释"为什么需要"）；统一 Python/MySQL 版本 |
| 测试 | pytest（后端单测 + API）+ Playwright（前端 UI）；由 AI 按规则生成，学生懂概念、看报告 |
| 安全 | 密码哈希、.env 存密钥、参数化 SQL、输入校验——写进规则文档由 AI 落实，学生了解即可 |
| LLM | 按项目需要自然接入，不硬塞 |

## 7. 三个项目方向

### Part 1 · 学习工具
以**英语学习工具**为例（功能直观、大家都想得到，便于说明），实际可以是任何学习领域（数学、编程、外语等）。
- **核心功能**：单词学习（词库、释义、例句）+ 练习（选择 / 填空）+ 错题本
- **AI（LLM）**：生成练习题、单词释义例句、错题解析
- **用户系统**：登录、学习进度、打卡
- **管理后台**：词库管理、题目管理、用户学习统计
- **技术**：Flask + MySQL + 前端（原生，AI 生成）

### Part 2 · 游戏
- **建议**：做 2D 游戏（3D 需要建模，太花时间）
- **要求**：至少要包含账号体系，需要带管理后台（账号 + 排行榜 / 存档等后端环节）

### Part 3 · 待定
